# Red — электронная очередь для MUP

Первая реализованная версия: FastAPI + PostgreSQL + React. Запись на день без назначенного времени; 100 мест на отделение; один паспорт — одна запись на дату; оригинал проверяется у окна; один сопровождающий без обслуживания.

Обновление этапов 1, 2а и 2б: вызовы/остаток дня, повторные эпизоды, восстановление доступа и безопасная замена паспорта готовы и установлены на homelab. План доводки и границы: [MVP_PLAN](docs/MVP_PLAN.md). Следующая задача — реальный вход и SMS/OTP.

## Запуск

Нужен Docker с Compose v2. В Windows запусти Docker Desktop. Из корня распакованного проекта:

```bash
docker compose up --build
```

Открой **http://localhost:8080**. Первая сборка скачивает образы и зависимости. Открывать frontend/dist отдельно не нужно: интерфейсу требуется сервер.

Compose включает **DEMO**. Роли «Заявитель», «Сотрудник» и «Администратор» доступны через меню профиля или «Сменить роль». Это намеренный тестовый вход, отключённый вне demo. Порт открыт только на 127.0.0.1.

Записи хранятся в PostgreSQL и переживают перезапуск. Остановка без удаления данных: `docker compose down`. Не используй `down -v`, если хочешь сохранить БД, файлы и ключи.

## Проверить основной путь

1. Открой «Записаться», войди как заявитель.
2. Выбери синтетический тестовый паспорт и подтверди поля.
3. Выбери день и сопровождение; подтверди запись.
4. В «Мои записи» появятся номер и QR-код. QR не заменяет документ.
5. Переключись на сотрудника, выбери тот же день и окно 1.
6. Вызови следующего; открой данные паспорта; отметь сверку оригинала.
7. Начни и заверши приём. В календаре место останется использованным.
8. Проверь «Живую очередь», полноэкранное табло и журнал администратора.

Повторный приём: в день исходной записи переключись на администратора, открой «Рабочее окно», выбери свободное окно и кнопку «Повторный приём A-…» у завершённого талона. Укажи причину, заново сверяй оригинал, начни/заверши эпизод. «История приёмов» сохранит первый результат и все повторы. Нового талона и места не появляется; после неявки/отмены повтора использованное место не освобождается.

Восстановление и замена паспорта: заявитель открывает «Мои записи», загружает действующий документ и отправляет запрос. Администратор очно проверяет оригинал, доступ к новому аккаунту и принадлежность документов одному человеку. Восстановление переносит связанную запись документа, её талоны и ожидание; прежние сессии отзываются. Замена создаёт новую неизменяемую версию того же документа. Старые реквизиты остаются зарезервированы, а места, талоны и дневные ограничения не обнуляются.

## Фото и OCR

Загрузку JPG/PNG обрабатывает отдельный worker с Tesseract. Пример: [синтетическое изображение](backend/tests/assets/synthetic_passport.png), явно помеченное TEST / NOT A VALID DOCUMENT.

На этом примере движок читает номер и даты, но ошибается в части имени; результат направляется на ручной разбор. Администратор открывает фото, сверяет поля и сохраняет решение с причиной. Заявитель обновляет результат, подтверждает данные и записывается. Это не подтверждение подлинности по фото.

## Реализовано

- Кабинет, запись, отмена, атомарный перенос, история и QR.
- 100 мест на день; глобальный дневной лимит документа; дополнительный лимит одной будущей записи на услугу.
- Три окна: вызовы, сверка оригинала, приём, завершение, пропуск, неявка и ограниченные исключения администратора.
- Публичное табло без персональных данных, обновление каждые 5 секунд.
- Лист ожидания: предложение, удержание на 10 минут, подтверждение, отказ, истечение.
- Закрытые зашифрованные фото, OCR/MRZ, ручной разбор, очистка фото.
- Сессии, CSRF, роли, ограничения запросов; OTP и адаптер SMS webhook.
- Проверяемые сотрудником запросы на восстановление доступа и замену паспорта; история версий и отзыв прежних сессий.
- Уведомления в кабинете, outbox, миграция, lock-файлы, Docker и тесты.

## Границы версии

SMS-провайдер не подключён: без явно настроенного webhook настоящие SMS не отправляются. Интерфейс пока русский. Один офис, одна услуга, три окна; это локальный MVP для проверки процесса, не официальная запись MUP.

Оставшиеся работы и точные ограничения: [IMPLEMENTATION](docs/IMPLEMENTATION.md). Для реальных паспортов и пилота нужны согласованный процесс ведомства, размещение, сроки хранения и внешние интеграции.

## Проверки

Изолированная тестовая БД, без очистки рабочих данных:

```bash
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from checks
docker compose -f compose.test.yaml down
```

Frontend без Docker:

```bash
cd frontend
npm ci
npm run check
npm test
npm run build
```

Backend с доступным PostgreSQL 16: `cd backend`, `uv sync --frozen`; задать DATABASE_URL и TEST_DATABASE_URL на отдельную БД с именем, заканчивающимся на `_test`; выполнить `uv run alembic upgrade head`, `uv run pytest -q`. Тесты очищают эту БД. В bash переменные задаются через `export`, в PowerShell через `$env:ИМЯ="значение"`.

После 2б прошли 90 backend-проверок на PostgreSQL 16.15, 4 frontend-проверки, TypeScript и production build. Проверена миграция 0003→0004 с существующими документами/талонами/claims, пустой откат/повтор и отказ удаления непустой истории доступа. На отдельной чистой серверной БД прошли **4/4 Chromium E2E**, включая замену паспорта. Серверные Docker-образы пересобраны 16.10.2026.

Для E2E нужен отдельный свежий демостенд с синтетическими данными: `npm run e2e`. Второй сценарий закрывает первый день и переносит тестовую запись, поэтому не запускать его на рабочей базе. `E2E_BASE_URL` задаёт адрес; необязательный `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` позволяет использовать установленный Chromium.

## Работа через Codex

Открой папку проекта в VS Code; начни с [STATUS](STATUS.md), [IMPLEMENTATION](docs/IMPLEMENTATION.md) и [первого промпта](prompts/01_START.md). AGENTS.md, инструкции backend/frontend, спецификации и task-файлы сохранены для продолжения. Новый scaffold создавать не нужно.

Фактический API: схема `/api/v1/schema` через web-порт. При прямом запуске backend также доступны `/docs` и `/openapi.json`.
